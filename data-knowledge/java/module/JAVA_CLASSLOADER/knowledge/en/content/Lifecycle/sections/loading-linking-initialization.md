A **ClassLoader** participates in turning a binary class name such as `demo.plugins.HelloPlugin` into a runtime `Class<?>`. It may locate and define the class directly or delegate the loading request to another ClassLoader. The JVM creates the runtime class from the loading result, then links and, when required, initializes it.

That distinction exists because a program is larger than the source files compiled in one command. A running JVM may need classes from the JDK runtime image, the application class path, modules, test tooling, plugin directories, generated bytecode, application servers, or other sources that were not all known as one fixed block when the JVM process started.

Without a loading subsystem, the JVM would need every executable type to be hard-wired into one closed image before startup. Java would lose important runtime capabilities such as loading an application dependency only when it is needed, isolating plugins, discovering providers, or hosting multiple applications with different dependency versions in one process.

In this module, a runtime **namespace** means the mapping from binary class names to runtime types visible/defined through a loader boundary. Two different loaders can both know the name `demo.plugins.HelloPlugin` while mapping it to two different `Class<?>` objects.

The running example uses a few architecture terms:

```text
host
→ the main application

plugin
→ an extension loaded by the host

Plugin API / SPI
→ a shared interface/contract between host and plugin

provider
→ an implementation of that SPI

framework/library
→ infrastructure code that uses the API/SPI to discover and invoke providers
```

### Binary name, class-file path, and class path are different concepts

Suppose the source is:

```java
package demo.plugins;

public final class HelloPlugin {
}
```

For this top-level class:

```text
binary name
→ demo.plugins.HelloPlugin

ordinary class-file path relative to a class-path root
→ demo/plugins/HelloPlugin.class
```

`ClassLoader.loadClass(...)` receives the **binary name**, not a filesystem path such as `/opt/app/demo/plugins/HelloPlugin.class`.

The **application class path** is best understood as a set of locations made visible to the application loader, for example directories and JARs:

```text
build/classes/java/main/
libs/plugin-api.jar
libs/plugins.jar
```

A loader can map:

```text
demo.plugins.HelloPlugin
        ↓
demo/plugins/HelloPlugin.class
```

and look for that relative entry under each class-path root. When a root is a JAR, the entry is inside the archive rather than an independent filesystem class file.

Keep these concepts separate. For a top-level class, some names may look textually similar, but **their roles are different**:

```text
source/package naming
binary class name
class-file/resource path
class-path location
```

> **Advanced — safe to skip on the first pass:** named modules add visibility and encapsulation rules. The basic model remains: **a loader receives a runtime name and locates a representation through the sources visible to it**.

### When does the JVM load a class?

Do not picture the JVM reading every class in every JAR at process startup. Loading is commonly **demand-driven**: a type is loaded/linked when the runtime needs it for execution, dependency resolution, reflection/dynamic loading, or while processing another type.

For example:

```java
import demo.plugins.HelloPlugin;

public final class Demo {
    public static void main(String[] args) {
        System.out.println("start");
    }
}
```

`import` is a **compile-time source-name feature**. It is not a runtime instruction and does not mean `HelloPlugin` has already been loaded or initialized when `Demo` runs.

Operations such as these can cause the runtime to need a type:

```text
new HelloPlugin()
using a member whose symbolic reference must be resolved
Class.forName("demo.plugins.HelloPlugin")
loader.loadClass("demo.plugins.HelloPlugin")
resolving a symbolic reference from another class
```

Do not depend on one universal exact load moment: a JVM may load or link some types earlier when the specification permits it, as long as observable Java semantics are preserved. The durable model is that **not every class is loaded at startup, and loading is still distinct from initialization**.

The broad lifecycle is:

```text
source code
    ↓ javac
class bytes
    ↓ loading
runtime Class object exists
    ↓ linking
verified + prepared + symbolic references resolved as needed
    ↓ initialization
static initialization runs when active use requires it
    ↓
normal execution
```

These words describe different responsibilities:

| Stage | Main question | Typical result |
| --- | --- | --- |
| Loading | Where are the bytes for this binary class name, and which loader defines them? | A runtime `Class<?>` exists. |
| Linking | Are the bytes valid, is static storage prepared, and what do symbolic references point to? | The class is safe and structurally connected enough for use. |
| Initialization | When should class initialization code actually run? | Static field initializers and static blocks have executed. |

The **defining ClassLoader** is especially important. For an ordinary named class/interface, it is the loader responsible for defining that runtime type, and it becomes part of the type's runtime identity. `Class#getClassLoader()` exposes that relationship, with bootstrap definitions represented as `null`. A loader may be asked to load a class but delegate the request to its parent; in that case the parent, not the requester, is the defining loader.

For the running example in this module, imagine a tiny plugin system:

```java
package demo.api;

public interface Plugin {
    String name();
}
```

The main application owns `Plugin`, while plugin implementations may come from another directory or JAR. The application therefore needs answers to several connected questions: which loader should own the API, which loader should define a plugin implementation, whether two same-named plugin classes are actually the same type, how a framework discovers plugin providers, and what must be released when a plugin is unloaded.

That gives the learning path for the module:

```text
Lifecycle
  → Built-in loaders
  → Parent delegation
  → Custom loaders
  → Class identity
  → Thread context ClassLoader
  → Resource loading
  → Initialization details
  → Unloading and leak prevention
```

The first rule to keep in mind is therefore simple: **"class bytes exist" and "the JVM has an initialized runtime class" are different states.**
