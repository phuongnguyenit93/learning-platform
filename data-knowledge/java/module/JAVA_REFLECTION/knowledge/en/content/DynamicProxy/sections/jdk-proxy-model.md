Before the API, start with the problem a proxy solves. Without proxy generation, logging can be added with a handwritten wrapper:

```java
final class LoggingPaymentGateway implements PaymentGateway {
    private final PaymentGateway target;

    LoggingPaymentGateway(PaymentGateway target) {
        this.target = target;
    }

    @Override
    public String pay(PaymentRequest request) {
        System.out.println("before pay");
        try {
            return target.pay(request);
        } finally {
            System.out.println("after pay");
        }
    }
}
```

That is perfectly reasonable for a few methods. When logging, authorization, or metrics must be repeated across dozens of interfaces and methods, however, many nearly identical wrappers appear. JDK Dynamic Proxy replaces that boilerplate with one model:

```text
typed interface call
        ↓
runtime-generated implementation
        ↓
one InvocationHandler receives Method + args
        ↓
shared interception/delegation policy
```

That is the **WHY** of JDK Proxy: callers retain a typed interface contract while dynamic cross-cutting behavior is centralized in one handler.

`Proxy.newProxyInstance(...)` needs three main pieces:

1. a `ClassLoader` used to define/resolve the proxy class;
2. the interfaces the proxy must implement;
3. an `InvocationHandler` that receives calls.

The example uses `PaymentGateway.class.getClassLoader()` because the loader that creates the proxy must be able to see the interfaces the proxy implements. That visibility constraint is enough for this chapter; class identity, delegation, and multiple-loader behavior belong to the following ClassLoader module.

```java
PaymentGateway target = new PaymentGatewayImpl(
        new PaymentService("stripe")
);

InvocationHandler handler = new LoggingHandler(target);

PaymentGateway proxy = (PaymentGateway) Proxy.newProxyInstance(
        PaymentGateway.class.getClassLoader(),
        new Class<?>[] { PaymentGateway.class },
        handler
);

String result = proxy.pay(new PaymentRequest("ORD-42", 150_000L));
```

The `proxy` object is not an instance of `PaymentGatewayImpl`. It is an instance of a class generated by the JDK at runtime, and that generated class implements `PaymentGateway`. The caller can therefore keep using a type-safe interface:

```java
PaymentGateway gateway = proxy;
gateway.pay(request);
```

while the actual call flow is:

```text
caller
  ↓ PaymentGateway.pay(...)
generated proxy object
  ↓ encode call as Method + args
InvocationHandler.invoke(...)
  ↓ optional logic
target / delegate
```

A dynamic proxy therefore keeps the interface contract while inserting an interception boundary between caller and implementation.
